# План реализации: датчики Apple Silicon и диагностика автоязыка

## Цель

Сделать Kelvin устойчивым на Intel и Apple Silicon:

- показывать только реально доступные и корректно идентифицированные датчики;
- не считать отсутствие вентилятора на MacBook Air ошибкой;
- не привязывать основные функции к одному жёсткому набору Intel SMC-ключей;
- собирать достаточную локальную диагностику для неизвестных моделей Mac;
- явно объяснять, почему автоязык не работает: разрешение, раскладки, режим или лицензия.

План предназначен для реализации другим агентом. Перед изменениями агент должен прочитать перечисленные ниже файлы и проверить актуальное состояние рабочей копии.

## Важные ограничения

1. Не требовать от пользователя изменения `boot-args`, загрузки в Recovery Mode, отключения SIP или других системных обходов.
2. Не считать любой ключ типа `sp78` температурой CPU. Тип описывает формат данных, но не физическое назначение датчика.
3. Не использовать неизвестный датчик как источник:
   - защиты от перегрева;
   - управления вентиляторами;
   - CPU/GPU hero-метрики;
   - критических уведомлений.
4. Не выполнять полное перечисление SMC-ключей в горячем цикле 1 Гц.
5. Не подменять недоступное значение нулём. Использовать `nil` и корректную деградацию UI.
6. Не ломать Intel-путь и уже известные ключи.
7. MacBook Air M1 является устройством с пассивным охлаждением. Отсутствие RPM на нём ожидаемо.

## Целевая архитектура

Добавить единый слой разрешения физических датчиков:

```text
AppleSMC
   ↓
SMC catalog: FourCC + type + size + readable value
   ↓
SensorResolver
   ├── verified model mapping
   ├── verified family mapping
   ├── known legacy fallback
   └── unknown/raw catalog only
   ↓
ResolvedSensorSet
   ├── cpuTemperature
   ├── cpuPackageTemperature
   ├── gpuTemperature
   ├── memoryTemperature
   ├── platformTemperature
   ├── batteryTemperatures
   └── fans
   ↓
SensorsModel / Alerts / Settings / fan profiles / diagnostics
```

`SensorResolver` должен отделять два понятия:

- ключ доступен и декодируется;
- физическое назначение ключа подтверждено.

Неизвестные, но читаемые ключи остаются в сыром каталоге. Они не получают автоматически имя CPU/GPU/Battery.

4. Сохранить обезличенный эталонный дамп в тестовых fixtures, например:

### Формат fixture

```json
{
  "model": "MacBookAir10,1",
  "architecture": "arm64",
```

## Этап 2. Ввести модель данных resolver

### Новый файл

Предпочтительно:

```text
Sources/SensorResolver.swift
```

### Предлагаемые типы

```swift
enum PhysicalSensorRole: String, Codable {
    case cpuTemperature
    case cpuPackageTemperature
    case gpuTemperature
    case memoryTemperature
    case platformTemperature
    case wifiTemperature
    case batteryTemperature
}

enum SensorConfidence: String, Codable {
    case modelVerified
    case familyVerified
    case legacyVerified
    case unknown
}

struct ResolvedSMCSensor: Equatable {
    let role: PhysicalSensorRole
    let keys: [String]
    let confidence: SensorConfidence
}

enum CoolingTopology: Equatable {
    case passive
    case active(fanIndices: [Int])
    case unknown
}

struct ResolvedSensorSet: Equatable {
    let modelIdentifier: String
    let sensors: [PhysicalSensorRole: ResolvedSMCSensor]
    let cooling: CoolingTopology
}
```

Точные имена можно скорректировать под стиль проекта, но необходимо сохранить:

- роль;
- список ключей;
- источник/доверие к маппингу;
- топологию охлаждения.

### API resolver

Resolver должен принимать абстракцию каталога, а не обязательно живой `SMC`, чтобы его можно было тестировать fixture-файлами:

```swift
protocol SMCInventory {
    var available: Bool { get }
    func keys() -> [SMCInventoryKey]
    func read(_ key: String) -> Double?
}
```

Не усложнять протокол без необходимости. Если текущая система тестов не поддерживает удобное внедрение зависимостей, допустим чистый метод:

```swift
static func resolve(
    model: String,
    architecture: String,
    catalog: [CatalogKey],
    values: [String: Double?]
) -> ResolvedSensorSet
```

### Критерий завершения

- Resolver является чисто тестируемым.
- Он не читает весь SMC-каталог каждую секунду.
- Он никогда не назначает физическую роль только по типу `sp78`/`flt`.

## Этап 3. Реализовать многоуровневый маппинг

### Порядок разрешения

1. Точный проверенный `hw.model`.
2. Проверенное семейство моделей/SoC.
3. Текущий проверенный legacy-набор Intel.
4. Нет подтверждённого соответствия: роль остаётся отсутствующей.

### Хранение маппинга

Создать одну каноническую таблицу, например внутри `SensorResolver.swift` или отдельного:

```text
Sources/SensorMappings.swift
```

Не размножать списки ключей по разным модулям.

Пример структуры:

```swift
struct SensorMapping {
    let modelPatterns: [String]
    let architecture: String?
    let roles: [PhysicalSensorRole: [String]]
    let cooling: CoolingTopology?
}
```

### Проверка кандидатов

Перед выбором ключа:

- ключ должен присутствовать в каталоге;
- тип должен поддерживаться декодером;
- значение должно читаться;
- температура должна быть конечной и находиться в допустимом физическом диапазоне, например `>-40 && <130`;
- для нескольких проверенных ключей допустимо использовать `max`, если это уже соответствует смыслу роли.

Диапазонная проверка отбраковывает мусор, но не доказывает назначение датчика.

### Критерий завершения

- Известные Intel-модели получают прежние роли.
- MacBook Air M1 получает только роли, подтверждённые реальным дампом.
- Неизвестная модель не получает выдуманный CPU/GPU-датчик.
- Все остальные читаемые ключи продолжают отображаться в сыром каталоге.

## Этап 4. Определять охлаждение корректно

### Логика

Основной сигнал:

- прочитать `FNum`, если ключ доступен;
- `FNum > 0` означает активное охлаждение с соответствующим количеством вентиляторов;
- `FNum == 0` на известной fanless-модели означает `.passive`;
- отсутствие `FNum` не должно автоматически означать пассивное охлаждение: использовать `.unknown`.

Дополнительная проверка:

- наличие согласованного набора `F{i}Ac`, `F{i}Mn`, `F{i}Mx`;
- индекс вентилятора должен попадать в диапазон `0..<FNum`.

Не использовать условие `F0Ac == 0` как доказательство отсутствия вентилятора.

### UI

Для `.passive`:

- не показывать ошибку;
- не показывать управление вентилятором;
- показать краткую нейтральную строку `Пассивное охлаждение` там, где пользователь ожидает информацию об охлаждении.

Для `.unknown`:

- показать прочерк или нейтральное `Данные недоступны`;
- не утверждать, что вентилятора нет.

Все новые строки добавить в `Sources/Localization.swift` для RU/UK/EN/PT и прогнать i18n-проверку.

### Критерий завершения

- На M1 Air нет ошибки «датчики не найдены» только из-за отсутствия RPM.
- Fan UI и fan control не предлагаются fanless-модели.
- Intel Mac с вентилятором сохраняет текущую функциональность.

## Этап 5. Перевести потребителей на единый resolver

Выполнять последовательно, сохраняя сборку после каждого шага.

### 5.1 `Sources/SensorsModel.swift`

- убрать локальные жёсткие списки ролей;
- получать ключи CPU/GPU/memory/platform/battery из `ResolvedSensorSet`;
- оставить существующие EMA, историю, форматирование и уровни;
- fan rows строить из `CoolingTopology` и разрешённых индексов.

### 5.2 `Sources/AlertsEngine.swift`

- брать только подтверждённый CPU temperature role;
- если роль отсутствует, не генерировать ложный перегрев;
- логировать однократно причину недоступности, без спама раз в секунду.

### 5.3 `Sources/NewSettings.swift` и `Sources/Settings.swift`

- превью текущей температуры должно использовать тот же role;
- UI fan settings должен учитывать `.passive`/`.unknown`;
- не дублировать fallback-списки.

### 5.4 `Sources/FanController.swift`

- профили должны использовать подтверждённые ключи;
- неизвестные температурные ключи нельзя автоматически включать в safety path;
- существующие пользовательские профили нужно мигрировать или оставить совместимыми.

### 5.5 `helper/fand.swift`

Это отдельный процесс и отдельная зона риска.

- Не передавать туда произвольные найденные `T***` только потому, что они читаются.
- Приложение должно передавать уже разрешённый и проверенный набор ключей.
- Сохранить текущую whitelist-проверку FourCC.
- При отсутствии всех разрешённых ключей демон должен вернуть системный fan auto, а не продолжать со случайным fallback.
- Не менять safety-поведение без отдельных тестов.

### 5.6 Остальные потребители

Найти остаточные жёсткие списки:

```bash
rg -n '"TCXC"|"TC0E"|"TG0D"|"TC0P"|"F0Ac"|"FNum"' Sources helper
```

Для каждого совпадения решить:

- это действительно низкоуровневый формат/legacy mapping;
- либо потребитель должен использовать resolver.

### Критерий завершения

- Канонические наборы физических датчиков объявлены в одном месте.
- Hero UI, алерты, настройки и fan logic не расходятся в выборе CPU/GPU датчика.
- Неизвестная модель деградирует безопасно.

## Этап 6. Расширить диагностический отчёт

Расширить существующий `Sources/DiagnosticReport.swift`, а не создавать отдельную кнопку.

### Добавить раздел «Оборудование и SMC»

- `hw.model`;
- архитектура (`arm64`/`x86_64`);
- версия macOS;
- `SMC available`;
- число перечисленных ключей;
- результат resolver:
  - роль;
  - выбранные ключи;
  - confidence;
- cooling topology;
- `FNum`, если читается;
- стандартные ожидаемые ключи, которые отсутствуют;
- читаемые температурные/fan-ключи:
  - FourCC;
  - тип;
  - размер;
  - значение либо причина отсутствия.

### Добавить раздел «Автоязык»

- сохранённый режим: off/hotkey/auto;
- фактически применённый runtime mode;
- Pro/trial доступ без лицензионного ключа и персональных данных;
- `AXIsProcessTrusted`;
- отдельный статус возможности создания/listen event tap;
- количество неудач создания tap и восстановлений, если эти счётчики доступны безопасно;
- текущий input source;
- список доступных keyboard layout input sources:
  - локализованное имя;
  - input source ID;
  - распознанный язык;
- найденные source/target пары для конвертации.

### Приватность

Не включать:

- набранные пользователем слова;
- содержимое буфера обмена;
- серийный номер;
- UUID;
- лицензионный ключ;
- имя пользователя;
- полный список процессов;
- сетевые адреса сверх уже осознанно существующего раздела отчёта.

### Формат

Основной отчёт оставить Markdown для человека. При необходимости добавить вложенный технический JSON-блок внутри Markdown либо отдельную internal-функцию экспорта JSON для fixtures.

### Критерий завершения

- Один отчёт объясняет, почему отсутствуют датчики.
- Один отчёт различает причины неработающего автоязыка.
- Отчёт не делает сетевых запросов.
- Отчёт не содержит пользовательского текста или идентификаторов устройства.

## Этап 7. Сделать состояние автоязыка наблюдаемым

Этот этап не меняет эвристику определения слов, пока диагностика не покажет, что проблема именно в ней.

### Добавить runtime status

Например:

```swift
enum LangRuntimeStatus {
    case off
    case unavailableByLicense
    case accessibilityDenied
    case inputMonitoringUnavailable
    case missingLayouts
    case tapStarting
    case active
    case tapFailed
}
```

Точный API должен быть потокобезопасным, так как event tap работает на отдельном потоке.

### UI

В настройках рядом с автоязыком показывать конкретный статус:

- работает;
- нужен Универсальный доступ;
- недоступен мониторинг ввода;
- не найдена пара раскладок;
- выключено лицензией;
- не удалось запустить обработчик клавиатуры.

Если режим сохранён как `auto`, но runtime выключен Pro-гейтом или разрешениями, UI не должен создавать впечатление, что функция работает.

### Разрешения

- Accessibility и возможность слушать события клавиатуры диагностировать отдельно;
- не открывать системные настройки циклически;
- после выдачи разрешения автоматически повторить запуск tap;
- не требовать перезапуска приложения, если macOS позволяет восстановиться без него.

### Критерий завершения

- По UI и отчёту однозначно видно, почему автоязык неактивен.
- В логах нет пользовательского текста.
- Текущие тесты `test/layout` продолжают проходить.

## Этап 8. Тесты

### Unit-тесты resolver

Добавить fixtures и проверки:

1. Известный Intel-каталог:
   - выбираются текущие CPU/GPU/battery ключи;
   - вентиляторы определяются по `FNum`.
2. MacBook Air M1 fixture:

   - каталог строится;

- статус отсутствующего Accessibility;

- tap failure;
- active;
- переход в active после выдачи разрешения.

Не пытаться создавать настоящий глобальный event tap в unit-тестах. Внедрить минимальный provider статусов разрешений/tap.

- приложение подключается к SMC либо честно сообщает, что SMC недоступен;

- CPU/GPU/battery temperatures не регрессировали;

- приложение не падает;
- raw-каталог доступен;
- неизвестные ключи не получают выдуманные физические имена;
- отчёт достаточен для добавления проверенного mapping в следующем релизе.

   - обезличенный дамп;
   - подтверждённые значения;
   - способ верификации CPU/GPU/battery роли.

## Definition of Done

Работа считается завершённой, когда одновременно выполнено следующее:

- MacBook Air M1 не показывает отсутствие вентилятора как ошибку.
- Доступные на M1 Air температуры отображаются из подтверждённого mapping.
- Неизвестные температурные ключи остаются сырыми и не участвуют в safety logic.
- Все основные потребители используют один resolver.
- Полный каталог SMC не перечисляется в цикле обновления.
- Диагностический отчёт объясняет выбор и отсутствие датчиков.
- Диагностический отчёт объясняет фактический статус автоязыка.
- Нет требований менять системные загрузочные настройки.
- Проходят unit-тесты, i18n-проверка и сборка.
- Выполнен ручной QA минимум на M1 Air и одном Intel Mac.

## Вопросы, которые нельзя решать догадкой

Если данных нет, агент должен остановить соответствующую часть реализации и запросить факты:

1. Реальный обезличенный SMC-дамп MacBook Air M1.
2. Какие ключи меняются синхронно с нагрузкой CPU/GPU.
3. Какие ключи подтверждены как батарейные.
4. Фактический вывод `FNum`.
5. Для автоязыка:
   - `AXIsProcessTrusted`;
   - результат создания event tap;
   - сохранённый и фактический режим;
   - список input source IDs;
   - состояние Pro/trial.

Без этих данных запрещено назначать случайный `sp78` главным CPU/GPU-датчиком или менять пороги эвристики автоязыка.
