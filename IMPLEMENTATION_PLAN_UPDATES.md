# План реализации: безопасные и бесшовные обновления Kelvin

## Цель

Заменить текущую схему «проверить JSON → открыть DMG в браузере» на полноценное обновление внутри приложения:

- проверка обновлений в фоне;
- проверка подлинности загруженного пакета;
- показ release notes;
- загрузка с прогрессом;
- установка и перезапуск без ручного копирования `.app`;
- корректное обновление установленного privileged service;
- откат или сохранение рабочей версии при ошибке.

План предназначен для другого агента. Он описывает ожидаемый результат, а не разрешает сразу переписывать updater без предварительного исследования выбранного фреймворка.

## Текущее состояние

- `Sources/Updater.swift`:
  - загружает `https://trykelvin.com/appcast.json`;
  - сравнивает версии;
  - проверяет `minOS`;
  - открывает URL DMG или release notes;
  - не загружает и не устанавливает обновление;
  - не проверяет подпись артефакта отдельно от HTTPS.
- `release.sh`:
  - собирает, подписывает, нотарифицирует и staple-ит DMG;
  - генерирует простой JSON appcast;
  - не генерирует криптографическую подпись update-архива;
  - не содержит staged rollout/channel metadata.
- Минимальная версия проекта сейчас включает macOS 11, поэтому выбранное решение обязано иметь явную стратегию для macOS 11–12.

## Архитектурное решение

### Предпочтительный вариант

Использовать зрелый macOS update framework с поддержкой:

- EdDSA-подписи update-артефактов;
- appcast;
- автоматической установки;
- relaunch;
- delta updates, если они реально нужны;
- пользовательского и фонового режимов проверки.

Основной кандидат — актуальная стабильная ветка Sparkle 2. Перед внедрением агент обязан:

1. проверить текущие официальные требования Sparkle;
2. проверить поддержку минимальной версии macOS Kelvin;
3. проверить совместимость с Developer ID, hardened runtime и notarization;
4. зафиксировать версию зависимости, не использовать плавающий branch.

Если Sparkle не подходит, собственный updater допустим только после отдельного security design review. Самописная установка приложения — существенно более рискованная часть, чем текущая проверка JSON.

## Неизменяемые требования безопасности

1. HTTPS недостаточно: update-артефакт должен иметь отдельную криптографическую подпись.
2. Приватный update signing key:
   - не хранится в репозитории;
   - не попадает в `.app`;
   - хранится в CI secret/keychain релизной машины;
   - имеет документированную процедуру ротации.
3. Публичный ключ встраивается в приложение.
4. Перед установкой проверяются:
   - update signature;
   - ожидаемый bundle identifier;
   - Developer ID Team ID;
   - версия;
   - минимальная версия macOS;
   - отсутствие downgrade, кроме явно подписанного recovery-процесса.
5. Release feed в production нельзя переопределить переменной окружения.
6. Не устанавливать пакет, если проверка подписи, кода или нотарификации не прошла.
7. Не удалять текущую рабочую версию до готовности проверенного replacement.

## Этап 1. Зафиксировать продуктовые решения

До кода принять решения:

- каналы: `stable`, нужен ли `beta`;
- автоустановка или только авто-download;
- разрешать ли «Установить при выходе»;
- политика пропуска версии;
- нужен ли staged rollout;
- срок хранения старых update-артефактов;
- минимальная поддерживаемая версия macOS;
- что происходит с несовместимым privileged service.

Рекомендуемый UX:

- автоматическая тихая проверка;
- ненавязчивый индикатор новой версии;
- кнопки `Установить и перезапустить`, `Позже`, `Что нового`;
- прогресс загрузки;
- понятная ошибка с `Повторить`;
- отдельный ручной пункт `Проверить обновления`.

## Этап 2. Внедрить update framework

### Файлы

- заменить или превратить `Sources/Updater.swift` в тонкий adapter;
- обновить `build.sh`;
- обновить `release.sh`;
- обновить `Kelvin.app/Contents/Info.plist` через исходный шаблон/сборочный процесс;
- добавить зависимость способом, совместимым с текущей не-Xcode сборкой.

### Требования к adapter

Весь остальной UI не должен напрямую знать API фреймворка:

```swift
protocol UpdateProviding {
    var automaticallyChecks: Bool { get set }
    var canCheckForUpdates: Bool { get }
    func checkInBackground()
    func checkManually()
}
```

Реальная форма может отличаться, но должна позволять:

- тестировать настройки без сети;
- заменить implementation;
- централизовать логирование;
- не размазывать update API по `Settings` и `main`.

### Миграция настроек

Сохранить пользовательское значение `updates.auto`.

Продумать миграцию:

- `updates.skip`;
- `updates.lastCheck`;
- новый канал обновлений;
- автоматическая загрузка.

## Этап 3. Новый appcast и релизный пайплайн

`release.sh` должен:

1. собрать приложение;
2. прогнать тесты;
3. подписать вложенные executable;
4. подписать основной bundle;
5. проверить подпись;
6. собрать подходящий update-архив;
7. нотарифицировать предусмотренный формат;
8. сформировать криптографическую update-подпись;
9. сгенерировать appcast;
10. проверить appcast схемой/валидатором;
11. только затем публиковать артефакты.

Appcast должен содержать:

- версию и build number;
- URL;
- размер;
- криптографическую подпись;
- minimum system version;
- release notes;
- дату;
- канал;
- критичность обновления, если используется;
- staged rollout metadata, если используется.

Генерация feed не должна вручную конкатенировать недоверенные значения без экранирования.

## Этап 4. Обновление privileged service

Основное приложение и root service имеют совместимые, но независимые версии.

Добавить handshake:

```text
appVersion
serviceProtocolVersion
serviceBuildVersion
minimumCompatibleServiceProtocol
```

После обновления приложения:

1. проверить состояние service;
2. если протокол совместим — продолжить без переустановки;
3. если service устарел — показать один понятный процесс обновления;
4. запросить системное одобрение только когда оно действительно необходимо;
5. проверить health после обновления;
6. при неудаче оставить управление выключенным и безопасно вернуть fan auto/BCLM 100 согласно политике.

Updater не должен самовольно подменять root-компоненты обходным shell-скриптом.

## Этап 5. Состояния и UX

Ввести модель состояния:

```swift
enum UpdateState {
    case idle
    case checking
    case available(version: String)
    case downloading(progress: Double)
    case readyToInstall
    case installing
    case current
    case failed(UpdateFailure)
}
```

Показывать человеку:

- текущую версию;
- дату последней успешной проверки;
- канал;
- состояние загрузки;
- понятную причину сбоя без технического мусора;
- кнопку копирования технической диагностики.

Не показывать modal alert при каждой фоновой проверке.

## Этап 6. Надёжность сети

- использовать ephemeral/ограниченную session configuration, если кэш не нужен;
- разумные таймауты;
- обрабатывать HTTP status;
- ограничить максимальный размер feed;
- запретить redirect на неподдерживаемую схему;
- не считать неудачную проверку успешной `lastCheck`;
- различать:
  - offline;
  - invalid feed;
  - invalid signature;
  - incompatible OS;
  - disk full;
  - installation failure.

Никакой update request не должен содержать лицензионный ключ, hardware UUID или пользовательские данные.

## Этап 7. Тесты

### Unit

- сравнение версий/build numbers;
- миграция настроек;
- stable/beta channel;
- incompatible `minOS`;
- skipped release;
- invalid feed;
- invalid URL/scheme;
- state transitions;
- service protocol compatibility.

### Integration

На локальном подписанном staging feed:

- нет обновления;
- доступно обновление;
- повреждённый архив;
- неверная update signature;
- неверный Team ID/bundle ID;
- обрыв загрузки и retry;
- недостаточно места;
- install and relaunch;
- обновление с установленным service;
- обновление без service;
- приложение запущено не из `/Applications`.

### Release gate

- `./test/run-tests.sh`;
- `codesign --verify --strict`;
- `spctl --assess`;
- notarization accepted;
- staple validation;
- feed validation;
- установка `N → N+1` на чистом Intel и Apple Silicon Mac.

## Этап 8. Документация и эксплуатация

Создать runbook:

- выпуск обычной версии;
- выпуск критического security update;
- отзыв ошибочного релиза;
- ротация update signing key;
- потеря signing key;
- временная остановка feed;
- rollback;
- диагностика update failure пользователя.

Обновить:

- `RELEASE.md`;
- `DISTRIBUTION.md`;
- `QA.md`;
- privacy-текст: update check является сетевым запросом и какие минимальные данные получает сервер.

## Рекомендуемые коммиты

1. `docs: choose update framework and channel policy`
2. `build: integrate signed update framework`
3. `refactor: wrap updater behind app adapter`
4. `build: generate signed appcast artifacts`
5. `feat: add update progress and install UX`
6. `feat: add helper compatibility handshake`
7. `test: cover update failures and migrations`
8. `docs: add update release and recovery runbook`

## Definition of Done

- Обновление устанавливается из приложения без ручного DMG/copy.
- Повреждённый или неподписанный артефакт не устанавливается.
- Текущая рабочая версия сохраняется при ошибке.
- Пользователь видит прогресс и понятный результат.
- Update check не передаёт лишние данные.
- Есть проверенный путь обновления app вместе с privileged service.
- Работает обновление минимум на macOS 11/12 fallback и современном macOS либо минимальная версия Kelvin официально изменена и задокументирована.
- Релизный runbook проверен реальным обновлением `N → N+1`.
