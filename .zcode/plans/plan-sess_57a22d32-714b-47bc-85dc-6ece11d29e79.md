
# План: Исправление HUD автокоррекции в Kelvin

## Подтверждённая первопричина

**Гипотеза подтверждена.** Кнопка «Вернуть» не работает из-за гонки (race) между CGEventTap и AppKit:

1. Пользователь кликает «Вернуть» → физический `.leftMouseDown` событие
2. CGEventTap (`.headInsertEventTap`) перехватывает событие **раньше** AppKit → `handle(type:event:)` вызывает `resetAll()`
3. `resetAll()` → `resetTypingState()` → **`lastConversion = nil`** и **`userTypedSinceConversion = true`**
4. Событие передаётся дальше в AppKit → `GlassButton.mouseDown` → `onClick` → `undoLastSpellCorrection()`
5. `undoLastSpellCorrection()` → `performOnTapThread` → guard проверяет `lastConversion` (уже nil) и `userTypedSinceConversion` (уже true) → **return без undo**

**Дополнительные найденные проблемы:**
- Многомониторный баг: `caretAnchor()` использует `NSScreen.screens.first?.frame.maxY` для конвертации AX→AppKit координат, что даёт неверный Y на неосновных мониторах
- Нет модели состояния с ID — один слот `lastConversion`, нельзя связать HUD с конкретным исправлением
- HUD может управлять исправлением, которое уже не актуально (после новых ввода/исправления)
- Нет явной инвалидации при перемещении каретки или смене приложения через клавиатуру (только при клике)
- Ordering race между `replace()` и `performOnTapThread` в `scheduleSpellCorrection` — краткое окно, когда заменённый текст уже в поле ввода, но `lastConversion` ещё не установлен

## Шаг 1: Введение `PendingCorrection` — модели исправления с ID

**Файл:** `Sources/PendingCorrection.swift` (НОВЫЙ)

Создать отдельный тип:
```swift
struct PendingCorrection: Equatable {
    let id: UUID
    let original: String
    let corrected: String
    let bundleID: String?
    let createdAt: ContinuousClock.Now
    var status: Status
    
    enum Status: Equatable {
        case pending, accepted, restored, invalidated
    }
    var isActive: Bool { status == .pending }
    var age: Duration { ContinuousClock.now - createdAt }
}
```

Почему `ContinuousClock.Now`: подходит для измерения коротких интервалов без проблем системных часов. Не `Date` — нет нужды в абсолютном времени.

Или даже лучше: отдельный метод `resetBufferOnly()`, который не трогает pendingCorrection вообще. Это основное исправление бага.

### 2d. Явная инвалидация pendingCorrection
Инвалидировать только по конкретным причинам:
1. **Новый ключевой ввод** (в `handleKeyDown`): `typedAfterPendingCorrection = true` (уже есть), плюс инвалидировать при вводе новой буквы (не modifier)
2. **Смена приложения** (в `handleFlags` при Cmd+Tab или в обработчике `frontmostBundleID` изменения): инвалидировать
3. **Новое исправление** перезаписывает старое — старое автоматически теряется
4. **Истечение таймера** (4.5s): HUD dismissal вызывает `acceptLastSpellCorrection()` — уже реализовано
5. **Клик вне HUD**: это допустимо оставить как «неявное принять» — pendingCorrection остаётся, но `typedAfterPendingCorrection = true` из resetTypingState предотвратит undo

## Шаг 3: Исправление `undoLastSpellCorrection` и `acceptLastSpellCorrection`

**Файл:** `Sources/LangSwitcher.swift`

### 3a. undoLastSpellCorrection с ID
```swift
func undoLastSpellCorrection(id: UUID) {
    performOnTapThread { [weak self] in
        guard let self,
              let pending = self.pendingCorrection,
              pending.id == id,
              pending.isActive,
              !self.typedAfterPendingCorrection
        else { return }
        self.replace(count: pending.corrected.count, with: pending.original)
        self.pendingCorrection?.status = .restored
        self.typedAfterPendingCorrection = true
        DispatchQueue.main.async { self.onFeedback?(.undo) }
    }
}
```
Ключевое: проверка `pending.id == id` — даже если pendingCorrection был перезаписан новым исправлением, undo старого откажется.

### 3b. acceptLastSpellCorrection с ID
```swift
func acceptLastSpellCorrection(id: UUID) {
    performOnTapThread { [weak self] in
        guard let self,
              let pending = self.pendingCorrection,
              pending.id == id,
              pending.isActive
        else { return }
        self.pendingCorrection?.status = .accepted
        self.typedAfterPendingCorrection = true
    }
}
```

### 3c. Обновить keyboard-based undo (`convertOrUndo`)
Адаптировать к новой модели — проверять `pendingCorrection?.isActive` вместо `!userTypedSinceConversion && lastConversion != nil`.

## Шаг 7: Тестирование — state machine

**Файл:** `test/correction/main.swift` (НОВЫЙ)

Создать тестируемую state machine без CGEventTap:
```swift
struct CorrectionStateMachine {
    var pending: PendingCorrection?
    var typedAfter: Bool = true
    
    mutating func applyCorrection(original: String, corrected: String, bundleID: String?) -> UUID
    mutating func undo(id: UUID) -> String?  // returns original if undone
    mutating func accept(id: UUID) -> Bool
    mutating func recordTyping()
    mutating func invalidate()
    mutating func newCorrectionInvalidateOld(original: String, corrected: String, bundleID: String?) -> UUID
}
```

Сценарии (10 штук из требований):
1. correction → undo → original restored
2. correction → accept → undo impossible
3. correction → typing → old undo rejected
4. correction A → correction B → undo A fails, undo B succeeds
5. undo(id:) does not invalidate before checking
6. click outside = typing = invalidate
7. app switch = invalidate
8. timer = accept
9. long words don't break
10. HUD stays in visibleFrame (positioning logic test)

## Ограничения подхода

- Не трогаем автопереключение раскладки и сниппеты (по требованию)
- Не делаем большой рефакторинг всего LangSwitcher — только замена LastConversion → PendingCorrection и разделение resetTypingState
- Хоткей немедленного отката: `convertOrUndo` уже работает — адаптируем к PendingCorrection
- Не используем задержки (delays) как исправление гонок — используем ID-based идентификацию

1. **Одна кнопка «Вернуть» + крестик закрытия** вместо двух равных кнопок — это делает «Вернуть» основным действием, но может быть непривычно
